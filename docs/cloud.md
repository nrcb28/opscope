# Read-only cloud collection

Opscope has a closed registry of eleven optional infrastructure providers: `azure`, `aws`, `gcp`, `oci`, `digitalocean`, `hetzner`, `cloudflare`, `openstack`, `alibaba`, `ibm` and `scaleway`, plus the separate `kubernetes` cluster adapter. `opscope cloud catalog` reads only local descriptors; it does not discover credentials or contact a provider. `cloud catalog --provider gcp` limits the output to one adapter. Each descriptor lists actual callable operations, resource types, permission prerequisites and experimental status. The newer adapters are experimental and expose deliberately limited evidence.

The core collector, offline analysis, reports, bundles and UI work without cloud accounts. Cloud operations use fixed command arrays or fixed HTTPS API routes. They do not start login, fetch secret values, install extensions, enable cloud services, run commands on machines, patch resources or change infrastructure. A registered provider is not proof that an authenticated scope is configured or reachable.

## Connections and provider accounts

The **Connections** menu provides setup guidance for the twelve registered sources. Its authenticated `GET /api/cloud/connections` endpoint reports local scope, credential and tool readiness plus the last observed action result. Reading it does not contact cloud services, start a process or initiate login. `authenticationActionsAvailable=false` and `remoteRequestsMade=false` describe that local guidance response.

The states remain independent. A configured scope only records an administrator-selected account/project/context. A credential marked `present` records local availability; existing CLI sessions and ADC can remain `external-unverified`. Tool availability does not establish valid authentication or read permission. `accessStatus` is `not-tested` until an existing configured action has run, and then preserves its last success, partial, no-data, configuration, permission, quota, timeout or failure state with an observation time. Even a successful read covers only that action's source and scope.

Provider guides contain fixed official signup, console and documentation links, along with command templates and required scope fields. Follow signup at the provider to create an account if needed. Run authentication commands on the host where Opscope runs, using the intended service user: for example, Azure CLI login, an AWS SSO/profile setup, or Google Cloud CLI login and the separately required ADC configuration. Token-based sources use the backend environment variables listed above. Opscope does not create accounts, acquire tokens through browser forms, change CLI profiles or run the guide commands. Refresh local readiness after external setup, then use **Test access** for an already configured scope. It selects the first configured read in this order: inventory, health, networks, metrics. It cannot submit a new account, endpoint or credential. Some operations still need additional options, enabled services or permissions even when the provider has a configured scope.

Cloud setup failures remain distinct from access to Opscope itself. Action responses use HTTP 409 for missing configuration, 424 for provider permission denial, 429 for quota, 504 for a read timeout, 501 for an unsupported operation and 502 for other provider failure. Useful partial evidence retains HTTP 200 with its coverage. These results do not invalidate an authenticated Opscope session. An Opscope HTTP 401/403 instead means its own session or request-source checks rejected the request.

| Observed problem | Next step on the Opscope host |
| --- | --- |
| Missing or untrusted CLI | Install the official CLI in a supported trusted location; an arbitrary executable on `PATH` is not sufficient. |
| Missing token or external authentication still unverified | Configure the backend credential or approved CLI/workload session as the service user. For GCP, check ADC separately from `gcloud auth login`. |
| Missing configured scope | Restart `serve` with the explicit authorized provider scope; the browser cannot expand it. |
| Provider permission denied | Check the selected account/project and the selected operation's read permissions. An authenticated CLI can still lack those permissions. |
| Provider quota or timeout | Wait before retrying a quota failure, or reduce the configured scope for a timeout. Repeating login does not resolve quota exhaustion. |

The last-read status is an observation, not a continuously monitored login state. A later credential expiry or permission change is discovered on the next configured read.

## UI scheduling, cache and retries

The server permits at most one active cloud read in a workspace, independently of host collection. A slow cloud request does not hold the host collector's gate. New cloud reads also have a two-second minimum interval per configured scope alias. These are local session limits, not a claim about the provider's actual quota.

A provider quota report returned with HTTP 429 starts a fixed fifteen-second local wait shared by operations of the same configured scope alias. Other configured aliases and host collection keep their own limits. The server supplies `Retry-After` and identifies whether a rejection came from the provider-quota wait, the scope's minimum interval or a busy cloud workspace. The fifteen-second fallback does not represent an upstream retry deadline or a quota shared by every account/process, and Opscope does not retry cloud reads automatically. Retry manually when the relevant control becomes available.

Completed redacted reports remain in a bounded session-memory cache: up to 32 reports, each no larger than 512 KiB. HTTP 200 ordinary reads remain cached for thirty seconds, HTTP 200 metrics for sixty seconds, and non-200 report responses for fifteen seconds. Larger reports are returned without being cached. A cache hit preserves the original report, status and observation time and makes no new provider request. The UI identifies reuse and shows its cache timing; refreshing setup checks alone does not replace provider evidence or bypass the cache.

Existing cached evidence can be returned during a scope wait. A cached quota response carries only the remaining local wait; reading it does not restart that wait. Cache expiry, access status and provider observation time remain distinct: expiry enables a later request but does not prove that the evidence is current or complete. Cache data is neither written to host history nor saved in browser storage. [Exact HTTP metadata and coverage contract](../src/Opscope.Api/README.md#cloud-catalog-fixed-scopes-and-report-cache).

For a browser accessing a remote server, configure the identities and environment on that server. [Remote hosting](remote-hosting.md) documents an authenticated same-host HTTPS proxy or an SSH tunnel. The proxy mode keeps Opscope on loopback and validates the explicit public origin; its upstream secret stays between the proxy and Opscope. All authorized users of one instance share that instance's configured provider scopes; this is not a per-user cloud account store or tenant authorization layer.

Google Cloud inventory includes selected Compute, GKE, Cloud SQL, Cloud Run and Storage **asset metadata**. The separate `services` operation adds whitelisted configuration/state: `--gcp-services gke,sql,storage` is the default, and selecting `run` requires an explicit `--region`. It reports GKE version/current-node counts, SQL HA/backup-enabled configuration, Cloud Run Ready/revision-observed metadata, selected ingress configuration and Storage access-prevention configuration where available. Service reads use exact gcloud projections: Cloud Run retains only the `run.googleapis.com/ingress` annotation, allowing `all`, `internal` or `internal-and-cloud-load-balancing`; other annotations and pod specifications are excluded. A missing ingress value remains unknown, and an invalid supplied value makes the read partial. The [v1 service metadata contract](https://github.com/googleapis/google-api-go-client/blob/main/run/v1/run-api.json) has no service update timestamp: `lastUpdatedAtUtc` has no value and may be omitted from JSON rather than substituting creation or Ready-transition time. The UI presents this as unknown. They do not read bucket objects or database contents, invoke service URLs or infer application availability. A backup-enabled setting does not prove restore readiness. Required reads include project identity plus the selected `container.clusters.list`, `cloudsql.instances.list`, `run.services.list` or `storage.buckets.list` permission. OS Config job evidence and the separate inventory-baseline comparison are described below.

GKE service metadata includes bounded node-pool observations from that same `container clusters list` response; it makes no additional API calls and adds no permissions. An exact canonical cluster `selfLink` must match the selected project, location and cluster name before child node-pool IDs are derived. Repeated canonical parents are omitted so they cannot duplicate a cluster or its pools. The allowlist retains pool status/version/initial node count, autoscaling enablement and per-zone/total bounds/location policy, and management auto-repair/auto-upgrade flags. Initial node count describes creation configuration, not current or desired pool size. It excludes node configuration, credentials, labels, service accounts, URLs and workloads. The reader examines at most one hundred source pool rows per cluster and 1,000 across the operation, including invalid rows. A real empty array establishes zero pools; an absent or malformed pool collection, invalid supplied fields, duplicates or truncation retains independent valid observations with partial coverage. Missing optional fields remain unknown without making an otherwise complete pool source partial. Per-cluster `properties.nodePools.state` describes pool-source coverage. An incomplete service read prevents its project from counting as a completed scope; a single-project partial read retains `completedScopes=0`. Autoscaling and management settings do not establish application health, security or verified control-plane identity.

The node-pool retention limit is separate from the shared redaction budget of 1,024 distinct identifiers. Project, cluster and child identities all use that budget, so a topology within the row limit can still exhaust it. Redacted output then omits text and non-schema keys with an explicit context-limit warning while retaining fixed schema keys, numeric evidence and finding severity. The maximum retained topology does not guarantee that all of its text remains available in a redacted export.

Cloud Monitoring, SCC, billing and OS Config reads use separately configured Application Default Credentials (ADC). Google Cloud uses the existing configured `gcloud` session and ADC; `--profile` is not a Google Cloud identity selector and is rejected before provider reads. Configure the intended CLI identity outside Opscope. The existing `gcloud` CLI session does not itself configure ADC. Configure ADC outside Opscope using your organization's workload identity or supported ADC workflow; the app never starts login. Tokens stay in the backend authentication flow and are never printed, persisted by Opscope or exposed to the browser. Monitoring requires `monitoring.timeSeries.list`/Monitoring Viewer and preserves a fixed fifteen-minute window with sixty-second mean alignment. Missing ADC or permission remains explicit partial/not-configured coverage; independent CLI inventory/state reads stay usable. A `gcp vm`/bundle local snapshot remains separate unless an independently supported identity check establishes the same resource; Google Cloud metadata linking is not implemented.

`gcp scc` reads existing global Security Command Center v1 findings for the selected project. Resource Manager first binds the configured project ID to its project number; returned finding resources must match that project. Required reads include `resourcemanager.projects.get` and `securitycenter.findings.list`, subject to SCC edition/configuration and IAM. An empty list or HTTP 403 is never a secure-project verdict.

`gcp cost` requires an existing export specified by `--billing-project <id> --billing-dataset <id> --billing-table <id>`, in addition to the authorized billed `--project`/`--projects`. It issues only table metadata and `tabledata.list` GETs, requiring `bigquery.tables.get`/`bigquery.tables.getData`; it creates no query, job, export or dataset. The table must be a supported existing billing-export table. Up to 1,000 observed rows are read across at most ten pages; client-side project filtering and currency-separated subtotals remain explicitly incomplete (`isComplete=false`). Credits are preserved, currencies are never added together, and missing rows mean unknown cost. These observations are neither a complete invoice nor a forecast. SCC/billing reads have thirty-second operation budgets, 4 MiB per response and 8 MiB aggregate response limits.

`gcp patches` reads metadata and aggregate results of existing OS Config patch jobs in the explicitly selected projects. Resource Manager verifies each project ID/number before the OS Config read. The reader omits free-text descriptions, script settings and arbitrary instance filters. It never starts a patch job, installs the OS Config agent or enables VM Manager. A successful historical job is not current compliance: `complianceState` remains `unknown`, and missing, stale or denied evidence cannot become a patched/healthy verdict. Required permissions are `resourcemanager.projects.get` and `osconfig.patchJobs.list`, using existing ADC with the cloud-platform scope. The operation accepts one to twenty projects and reads at most ten pages per project, 1,000 jobs and sixty HTTP requests overall, with a thirty-second operation deadline, 4 MiB per response and 8 MiB aggregate. Job create/update timestamps remain provider observations; an update older than twenty-four hours is marked stale, while a missing timestamp remains unknown. Missing aggregate counters remain null rather than zero.

`gcp drift` requires `--baseline <path>` pointing to a private, unredacted JSON export of a compatible `gcp inventory` run. It compares resource presence and only shared known `region`/`state` values, with the same explicit projects, region/resource filters and asset-type provenance. GCP inventory scope records `profile: null`; a non-null profile in a baseline is rejected because it does not prove a selected Google Cloud identity. If either inventory has partial coverage, the reader suppresses added/missing assessments while retaining comparable fields on resources observed in both. Redacted or invalid identities, malformed input and mismatched scopes prevent comparison; missing or redacted attributes remain unknown. Regenerate older exports that lack the inventory-scope metadata. The input limit is 16 MiB and 10,000 resources, with bounded JSON depth and complexity. Incomplete enumeration cannot establish an absent resource, and missing attributes cannot establish complete conformance. This is a comparison of two observations, not a Terraform plan, deployment or proof of continuous compliance; raw HCL, Terraform state and arbitrary JSON properties are not supported for this GCP workflow.

Cloud metric histories are provider observations, separate from the five-second host sampler. Hetzner CPU history requests a sixty-second step over the preceding hour, caps reads at ten enumerated servers and retains the provider's returned period, unit and timestamps. DigitalOcean retains cumulative CPU seconds per CPU/mode for at most ten project-allowlisted droplets; these are not instantaneous CPU percentages. A response without observations remains `no_data`, not a zero series. Histories are bounded to 1,000 series/10,000 points per collection; resource/read limits can produce explicit partial coverage.

The supplemental readers use a fixed last-hour window. OCI returns CPU utilization percentages with sixty-second means in the selected compartment; it does not traverse subcompartments. OpenStack Gnocchi measures preserve native units: cumulative CPU nanoseconds remain nanoseconds and memory measures retain their declared byte/MB/MiB units. Cloudflare returns five-minute request/byte/cache counts for at most twenty explicitly selected zones after checking zone ownership. Alibaba requests sixty-second CloudMonitor CPU utilization for at most ten authorized ECS instances and preserves the actual period returned by the provider. IBM Monitoring and Scaleway Cockpit expose the `up` scrape-target gauge, a ratio of zero or one; it is not CPU usage or proof of application availability. These readers do not change cloud resources, refresh measures or retry quota failures automatically. Missing agents, telemetry services or permissions remain explicit. The UI keeps each unit/source separate from host CPU/RAM.

## Selected posture and regional network reads

`digitalocean inventory` and `digitalocean posture` require an explicit `--project <uuid>` and the existing backend `DIGITALOCEAN_ACCESS_TOKEN`, acquired and renewed outside Opscope. A fixed `GET https://api.digitalocean.com/v2/projects/{project}` must return the selected project ID before resource reads. This verifies the selected project, not a separate account/team identity. The paged `/v2/projects/{project}/resources?per_page=100&page=N` list supplies canonical resource URNs; it only returns resources visible to the token. A completed visible list never proves complete account/team coverage or the absence of resources hidden by permissions. The [official project-resource contract](https://github.com/digitalocean/openapi/blob/main/specification/resources/projects/projects_list_resources.yml) requires `project:read` plus the read scope for each visible resource.

Inventory reads only listed droplets, volumes and load balancers through fixed `/v2/droplets/{id}`, `/v2/volumes/{uuid}` and `/v2/load_balancers/{uuid}` GETs, validating the returned identity against its project URN. VPC reads use `/v2/vpcs/{uuid}` only for `vpc_uuid` references from those verified droplets/load balancers; the returned VPC ID and region must match. A VPC can be shared, so this is a resource relationship rather than exclusive project ownership. Required read scopes are `project:read`, `droplet:read`, `block_storage:read`, `load_balancer:read` and `vpc:read`, according to the observed resource types. Posture reads selected droplets and paged `/v2/firewalls` metadata with `project:read`, `droplet:read`, `firewall:read` and `tag:read`. It checks direct `droplet_ids` membership and exact tag intersection with selected droplets. Missing membership fields remain unknown and make coverage partial; explicit empty arrays support observed zero membership. Incomplete project membership is inherited by dependent checks rather than becoming a complete empty result. Any valid IPv4/IPv6 CIDR with prefix length zero is global ingress; an uninterpretable supplied rule leaves the global-rule count unknown instead of zero. Observed global-ingress configuration does not establish an effective network path.

The DigitalOcean inventory/posture reader retains allowlisted configuration and aggregate membership/rule observations, omitting names, tags, addresses/CIDRs, raw rules, certificates and service URLs. Its `configurationEvidence.source=digitalocean-project-fixed-read` carries `scopeVerification.source=digitalocean-project-v2` and independent checks: inventory uses `project-resources`, `droplets`, `volumes`, `load-balancers` and `vpcs`; posture uses `project-resources`, `droplets` and `firewalls`. Limits are sixty seconds, sixty GETs, at most ten one-hundred-row pages per list, 1,000 source rows overall, 4 MiB per response and 8 MiB aggregate response bytes. The shared row budget counts project-membership rows, resource-detail rows and firewall rows; it is not a promise of 1,000 retained resources. Per-resource GETs can exhaust the sixty-query budget before the row limit. A `ratelimit-remaining: 0` response is retained, but no subsequent GET is sent; HTTP 429 is not retried. Quota, deadline, malformed identity/pagination and budget failures stop further affected reads and retain explicit partial/unavailable evidence, without retries. Expected counts are known only when their prerequisite membership/reference reads completed; the global firewall total is never used as a project total. Health and native cumulative-CPU metrics retain their separate existing readers and coverage; the new project preflight is specific to inventory/posture. See the official [droplet](https://github.com/digitalocean/openapi/blob/main/specification/resources/droplets/droplets_get.yml), [load-balancer](https://github.com/digitalocean/openapi/blob/main/specification/resources/load_balancers/loadBalancers_get.yml), [VPC](https://github.com/digitalocean/openapi/blob/main/specification/resources/vpcs/vpcs_get.yml) and [firewall](https://github.com/digitalocean/openapi/blob/main/specification/resources/firewalls/models/firewall.yml) contracts.

`cloudflare posture` requires an explicit account and one to twenty distinct zone IDs. `--cloudflare-checks tls,dns,waf,routes` chooses the reads, with `tls` as the default. Zone Read is required to verify each zone ID and account before any selected check. TLS reads require Zone Settings Read; DNS, WAF and Workers-route reads require the corresponding resource-restricted read permissions. The TLS evidence contains only allowlisted SSL/minimum-version/HTTPS settings. DNS observations contain aggregate type/proxied counts; WAF observations contain selected entrypoint rule metadata/counts; Workers routes expose counts. DNS names/content/TXT, WAF expressions/descriptions/parameters and Worker patterns/script names are excluded from reports. Missing WAF entrypoints or inaccessible products remain unknown, never a disabled-WAF or secure-zone verdict. A weak TLS setting or paused-zone finding records observed configuration; it does not test traffic or application availability. The operation has a thirty-second deadline, sixty HTTP reads, 4 MiB per response and 8 MiB aggregate response limits. DNS uses at most ten pages of one hundred rows; selected DNS/rule/route observations share a 1,000-row budget across the authorized zones.

`alibaba posture` uses the existing CLI identity and verifies its STS account against `--account` before disk or security-group reads in the explicit region. `--security-groups <sg-id,...>` optionally restricts group reads to one to twenty IDs; bounded enumeration is used otherwise. That allowlist does not narrow the separate disk read, which retains the explicit account/region scope. The reader uses exact `--cli-query` projections before CLI output enters Opscope, omitting descriptions, tags and arbitrary properties. Selected group/rule metadata identifies observed global ingress and administrative-port configuration. Unknown direction, policy or port data remains incomplete evidence. Allow rules do not prove an effective path: priorities, drop rules, attachments, routing and external controls require their own interpretation. The same STS-verified operation reads projected `DiskId`/`RegionId`/`Encrypted` fields and retains the disk-encryption finding; missing encryption metadata remains unknown. Required reads are `sts:GetCallerIdentity`, `ecs:DescribeDisks`, `ecs:DescribeSecurityGroups` and `ecs:DescribeSecurityGroupAttribute`, using an installed CLI version that supports `--cli-query`. Limits are thirty seconds and sixty CLI reads overall, at most ten pages for disks, ten for group enumeration and ten rule pages per selected group, with at most twenty groups and 1,000 disk/rule rows overall. Projected output is limited to 4 MiB per command and 8 MiB in total. Each source retains its own coverage, and throttling stops further reads.

`ibm networks` requires one explicit `--account <32-lowercase-hex-id> --resource-group <32-lowercase-hex-id> --region <region>` and an existing backend `IBM_CLOUD_IAM_TOKEN`, acquired and renewed outside Opscope. Supported regions are `us-south`, `us-east`, `eu-gb`, `eu-de`, `jp-tok`, `jp-osa`, `au-syd`, `ca-tor`, `br-sao` and `eu-es`; `--zone` does not narrow this regional read. First, a fixed `GET https://resource-controller.cloud.ibm.com/v2/resource_groups/{group}` must return the selected group ID and account ID. A failed preflight prevents VPC product reads. It requires Viewer on the targeted resource group, separately from VPC resource permissions. The [official IAM action reference](https://github.com/ibm-cloud-docs/iam/blob/master/iam-service-roles.md) maps VPC Viewer to `is.vpc.vpc.list`/`is.vpc.vpc.read`, subnet Viewer to `is.subnet.subnet.list`/`is.subnet.subnet.read`, and security-group Viewer to `is.security-group.security-group.read`. It does not document a separate security-group list action. Grants on a container do not automatically grant access to its child resources; verify effective scope and permissions for the selected account.

The IBM reader uses only fixed regional `https://{region}.iaas.cloud.ibm.com/v1/vpcs`, `/subnets` and `/security_groups` GETs with `version=2026-10-06`, `generation=2` and `resource_group.id` filtering. Before retaining metadata it validates resource-group membership and the exact resource/account/region CRN; a subnet must also match its exact returned zone in the selected region. CRNs are validation inputs and are omitted from evidence. The allowlist retains VPC status/classic-access configuration, subnet status/IP version, security-group rule/target counts and redacted VPC references. It omits names, tags, IPs, CIDRs, raw rules, target identities, routes and gateway configuration. Missing optional fields/counts remain unknown; explicit arrays establish observed counts. The operation has a thirty-second deadline, at most ten one-hundred-row pages per product, thirty-one GETs including preflight, 1,000 resources overall, 4 MiB per response and 8 MiB aggregate response limits. `configurationEvidence.source=ibm-vpc-fixed-read` carries scope verification and independent `vpcs`, `subnets` and `security-groups` checks with observed/expected resource counts. Only a verified scope and a completed read with an explicit zero total establish an empty product result. Denied reads, malformed identities, pagination mismatches and safety limits preserve unavailable or partial coverage. Counts and lifecycle settings do not establish effective access, isolation, reachability or application health. See IBM's [Resource Manager client](https://github.com/IBM/platform-services-go-sdk/blob/main/resourcemanagerv2/resource_manager_v2.go), [regional endpoints](https://github.com/ibm-cloud-docs/vpc/blob/master/vpc-endpoints.md) and [VPC V1 API version contract](https://github.com/IBM/vpc-go-sdk/blob/master/vpcv1/vpc_v1.go).

`scaleway networks` requires `--project <uuid> --region <region>` with an explicit supported region (`fr-par`, `nl-ams` or `pl-waw`). It does not derive a region from `--zone`. Fixed `vpc/v2/regions/{region}/vpcs` and `/private-networks` GET routes enumerate the two resource types, with a fixed project filter and exact validation of each returned ID, project and region. Grant read access to VPC and Private Network in that project. Selected metadata includes supported boolean configuration and a redacted VPC reference; names, tags, CIDRs and subnets are omitted. The read has a thirty-second deadline, at most ten one-hundred-row pages per resource type, twenty GETs, 1,000 resources overall, 4 MiB per response and 8 MiB aggregate response limits. These properties do not prove isolation or connectivity. Gateways, load balancers, ACLs and route queries are outside this operation. Instance inventory/health keeps its zone scope, and Cockpit metrics retain their separate source verification.

These checks use credentials only in backend reads. Selected options are bound when `serve` starts; the browser cannot supply new IDs, endpoints or credentials. Each read carries its source, observation time and coverage. Empty observed counts, missing observations, denied reads and partial enumeration remain distinct. The configuration view presents allowlisted fields and its JSON projection excludes unsupported configuration properties; this projection does not expand the backend evidence or its coverage.

## Kubernetes cluster scopes

An existing administrator-approved kubeconfig context and one to twenty explicit namespaces are mandatory. `--namespace <name>` is the single-namespace alias. No browser request can supply kubeconfig, a cluster endpoint, bearer token or an all-namespaces wildcard. `serve --cloud kubernetes --kubernetes-contexts <context> --namespaces <names>` binds those choices before printing the session URL. Context and namespace identifiers remain redacted in shared evidence.

The fixed kubectl metadata projections cover pods, deployments, statefulsets, daemonsets, services and safe event type/reason/time/count fields. They omit pod environment/commands, raw specs, event messages, Secrets, ConfigMaps and logs. The adapter never runs exec, port-forward or mutation commands. Nodes are cluster-scoped and are queried only with `--kubernetes-nodes`; remove that opt-in when namespace-only RBAC is required. Context authentication uses the existing approved CLI configuration.

Inventory/health verifies each selected namespace using `get namespaces <name>`; grant cluster-scoped `get` constrained with `resourceNames`, without granting namespace enumeration. Workload/service/event reads can use `get`/`list` in per-namespace Roles. Metrics only needs the selected namespaced `metrics.k8s.io` pod reads and verifies returned namespace identities. Node reads need separate cluster-scoped access. The adapter installs neither RBAC nor Metrics Server. Projected output is limited to 1 MiB and ten seconds per kubectl invocation, 1,000 resource rows and sixty seconds per collection; kubectl manages its own 100-item server chunks within those budgets. Missing permissions or Metrics Server cannot become a zero measurement.

Pod metrics are single recent observations in CPU millicores and memory bytes, with the provider timestamp/window. They are not percentages or a retained cloud history. The UI displays their values and sample tables even when there are too few points to draw a line.

Node-to-infrastructure matching is an additional opt-in: `--kubernetes-nodes --infrastructure-provider gcp` with an explicit project scope, or `--infrastructure-provider azure` with an explicit subscription scope. Opscope reads the selected provider inventory in the backend and compares canonical node `providerID` references against normalized resources in that scope. Matching is exact against successful inventory and cluster observations no older than five minutes; timestamps more than two minutes in the future are rejected. Google Cloud also requires explicit complete coverage; Azure requires successful inventory without incomplete/truncation warnings and honors explicit coverage when present. Duplicate node references or ambiguous infrastructure IDs do not establish a verified link. Names alone do not establish a link. Azure VM scale-set identities are outside the supported VM inventory and remain unverified. A verified match establishes only the observed node reference, not control-plane identity, cluster ownership, host identity or application availability. AWS node references lack an independent account binding in this workflow and remain unverified. The result distinguishes all observed node references matched, some matched, and no verified match. It reports only observed links, with at most 1,000 nodes and 10,000 infrastructure resources across twenty reports. No browser request can supply provider IDs, inventory contents or new scopes.

## Configure the local Cloud workspace

The server binds providers, operations and scopes before printing the session URL. For example:

```sh
opscope serve --cloud azure,aws,gcp --subscriptions <subscription-id> --profiles audit --gcp-projects <project-id> --regions eu-west-1
opscope serve --cloud digitalocean --digitalocean-projects <project-uuid>
opscope serve --cloud openstack --cloud-name production-reader --openstack-projects <project-id> --region RegionOne
opscope serve --cloud kubernetes --kubernetes-contexts <reader-context> --namespaces monitoring,application
opscope serve --cloud gcp --gcp-projects <project-id> --baseline baseline.json
opscope serve --cloud cloudflare --cloudflare-accounts <32-hex-account-id> --zones <32-hex-zone-id> --cloudflare-checks tls
opscope serve --cloud scaleway --scaleway-projects <project-uuid> --zone fr-par-1 --region fr-par
opscope serve --cloud kubernetes --kubernetes-contexts <reader-context> --namespaces application --kubernetes-nodes --infrastructure-provider gcp --project <project-id>
```

A session accepts the twelve registered source adapters and at most twenty total scope choices. New adapters require an explicit scope. The browser receives anonymous labels such as `gcp-scope-1`, never a free-form scope selector. Provider-specific allowlists prevent a Google Cloud project ID being reused as a DigitalOcean project: `--gcp-projects`, `--digitalocean-projects`, `--hetzner-projects`, `--openstack-projects`, `--scaleway-projects`, `--oci-compartments`, `--cloudflare-accounts`, `--alibaba-accounts`, `--ibm-accounts` and `--kubernetes-contexts`. Generic `--projects`, `--compartments`, `--accounts` or `--contexts` apply only where that scope type is intentional. Region/profile/namespace/token context remains fixed for the session; use separate sessions for sources needing different values of a shared option.

Only advertised read actions with server-bound configuration are exposed in the workspace. Google Cloud drift is available only when an inventory baseline path is configured at server startup with `--baseline`; the browser cannot select a local path or submit a baseline. VM/instance, bundle, Azure/AWS drift, Arc and identity metadata commands remain explicit CLI workflows. Changing a provider in the UI cannot discover new accounts, install credentials or expand the server allowlist.

CLI executables must come from trusted installation locations, not the working directory or an arbitrary PATH entry. On Unix use the supported root-owned system/vendor locations (for example `/usr/bin`, `/usr/local/bin`, or the documented vendor `/opt` directory). On Windows the additional provider CLI executables use `%ProgramFiles%\Opscope\CloudTools\<tool>.exe`; install/manage those binaries as administrator. Existing Azure/AWS trusted locations remain supported. Configure CLI authentication outside Opscope, and do not place API tokens in arguments or snapshot files.

`cloud` detects Azure/AWS through identity-only IMDS/IMDSv2 only when explicitly invoked without `--provider` and with an operation other than `catalog`. New providers require an explicit `--provider`/direct command and configured scope. AWS never falls back to IMDSv1 or reads the IAM credentials metadata paths. Azure reads compute identity, not a Managed Identity token endpoint. Metadata requests use a fixed link-local endpoint, no proxy/redirect, strict bounds and short deadlines. `--cloud-context` enables the same optional lookup for other commands.

VM/instance reports include a separately labelled local snapshot. A local-to-cloud match is asserted only when identity metadata matches the selected normalized resource, including AWS account and region. Without a match the evidence remains explicitly unlinked. Local Arc connection metadata comes from trusted `azcmagent show --json`; SSM service installation/running state never implies cloud Online status. `environment` reports these local signals. No hybrid agent is installed or enrolled.

## Permissions and scopes

Azure Reader and Monitoring Reader are starting points for resource/monitor queries. Verify the effective role assignments, scopes and API permissions required by your tenant. Resource Graph, Defender, Update Manager, Health and Monitor may expose different coverage depending on identity and service configuration. Missing permissions or services produce explicit warnings; Opscope never enables paid capabilities.

[cloud-readonly-iam.json](cloud-readonly-iam.json) is an action-level AWS policy example covering the implemented read APIs. It deliberately contains no write, credential-value, Secrets Manager or Lambda environment actions. Some APIs require wildcard resources for account-wide inventory. Remove optional statements and constrain supported resources, regions, accounts and role trust for your deployment. The example has not been attached to a live identity or validated against your organization's IAM conditions.

Use SSO, instance roles, Managed Identity sessions or configured role profiles instead of long-lived keys. AWS cross-account traversal uses `--profiles` with already configured CLI profiles; role chaining remains in the normal AWS CLI configuration. `--accounts` is an account filter and does not create sessions. Delivery permissions are separate: this reader policy does not grant CloudWatch log writes or ticket creation.

## Drift, cost and incomplete evidence

Google Cloud drift accepts only the compatible unredacted normalized inventory export described above; its exact scope is required, and added/missing assessments require complete coverage in both observations. AWS drift supports normalized unredacted exports and a documented subset of Terraform JSON state, plus existing CloudFormation drift records. Azure supports normalized exports and supported ARM/Terraform JSON identities and attributes; see [azure-drift.md](azure-drift.md). Compile Bicep to ARM JSON outside Opscope. Raw HCL/Bicep, expressions that cannot resolve to resource identities, unsupported properties and redacted/unscoped inputs are not silently treated as compliant. No deployment, plan, drift-start or IaC execution is initiated.

Terraform state and full exports can already contain sensitive data. Keep input files private. Output comparisons report changed field names rather than arbitrary expected/actual values. Default report output redacts resource identifiers; generate an explicitly protected `--full` export when a later exact baseline comparison requires identities.

Azure/AWS cost commands report orphan candidates and observed CPU underuse with documented sample windows. Google Cloud cost reads the explicitly configured export rows described above. None deletes/resizes resources or promises monetary savings. Cloud API, monitoring and ingestion charges depend on provider/account terms.

Reports distinguish `operationSucceeded=false` for failed required work from optional coverage warnings. CLI failure returns `2`; findings use the selected `--fail-on` threshold. Add `--require-complete` to reject any warning. An empty successful inventory remains different from an unavailable inventory.

No live tenant/account was used in the automated tests. Providers, pagination, identity validation, drift and permission failures are tested with injected CLI/HTTP transports.
